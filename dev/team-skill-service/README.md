# Team Skill service (deterministic local fixture)

English | [中文](README.zh.md)

An in-memory HTTP service that stands in for the production AI Coding account, project, and Team Skill APIs while the plugin, Host, and Web admin are developed and acceptance-tested. It is a fixture: nothing in it is production infrastructure, and fixture behavior is not production acceptance evidence.

## Scope and boundary

- Production persistence, password hashing, credential delivery, organization directory, artifact storage, and aggregation services are owned by the backend team and are out of scope here.
- Fixture-only properties, kept because deterministic local integration needs them: account passwords are stored and compared in plaintext in memory; seeded demo accounts ship fixed passwords and fixed sessions (`admin-demo`, `manager-demo`, `demo-token`); account creation returns the one-time initial password in the HTTP response; every response carries `access-control-allow-origin: *`.
- P0-01 boundary: none of the fixture tests constitute production evidence. Real IAM, password hashing, persistence, artifact storage, audit storage, origin allowlists, and cross-instance consistency remain colleague-owned prerequisites and stay BLOCKED until a production backend is delivered.
- A production deployment must replace each of these: hashed credentials with invite and password-change delivery, server-issued short-lived sessions, the real organization directory, a deployment-configured origin allowlist, and protected artifact storage. Deploying these routes as-is would expose credentials and allow any browser origin.

## Authorization model

- Skills are authored under one organization, resolved from the author's active memberships; admin authors must pass an explicit `organization_id`.
- Regular-user Skill surfaces (catalog, detail, release-status, installation, download) are installable reads: the caller must reach the project, the Skill's organization must equal the project's organization, the Skill must be bound to the project as a `skill` asset relation, the caller must be inside the Skill's visibility scope in that organization, **and the Skill plus the requested version must both be `published`**. A bound-but-unpublished Skill (draft, pending_review, approved, withdrawn) returns the same 404/empty semantics as a missing resource on every regular-user path and never leaks its metadata or existence. The requested version must also be the Skill's **current** published release: adding a new draft version turns the Skill back to draft, and installations of the older published version are rejected from that moment (catalog, detail, release-status, installation, and every previously issued download URL alike).
- Governance reads are a separate authorization: management routes (`/v1/admin/team-skills`) use organization-scope management checks, not the installable gate, so authorized managers and admins can inspect draft, pending_review, approved, and withdrawn Skills.
- The publication rule: publishing makes a version installable, and binding the Skill to a project as an asset makes it discoverable in that project's catalog. An unbound published Skill is invisible to every project catalog; the admin Skill view shows the bound project ids so the missing step is visible next to the publish state.
- Management reads and writes are scoped by organization: admin spans the platform, a manager spans their active organizations. People and group visibility targets must be active members or groups of the Skill's organization directory.
- Suspension, membership removal, and asset unbinding take effect on the next request. A download URL is re-authorized on every request against the current Skill status, the operation's version, the project binding, the organization, the visibility scope, and the operation owner; a Skill or version that leaves `published` (or a removed binding) immediately revokes every previously issued download URL with **403 `INSTALL_AUTHORIZATION_REVOKED`** — a different response from the 404/empty semantics of detail, catalog, and release-status, because the URL was already issued. The Host quarantines an installed copy once the authoritative release-status response no longer reports it as published.
- Response semantics per surface: detail of an unpublished Skill returns `404 RESOURCE_NOT_FOUND`; catalog and release-status simply omit non-installable resources (no forged records); a new installation of a non-published or non-current version returns `404 RESOURCE_NOT_FOUND`; a revoked download returns `403 INSTALL_AUTHORIZATION_REVOKED` with `data: null` and no artifact bytes.

## HTTP contract

- Every JSON response uses one envelope: `{code, message, request_id, data}` with `code: 0` on success and `data: null` on failure. The one exception is a successful artifact download, which returns the raw `application/zip` bytes instead of the JSON envelope.
- Missing or empty required fields return `422 VALIDATION_REQUIRED`; wrong field types and invalid enum values return `422 VALIDATION_ERROR`; malformed JSON returns `400 INVALID_JSON`. Missing `Idempotency-Key` on a write returns `400 IDEMPOTENCY_KEY_REQUIRED`. Each route keeps its existing check order for `Idempotency-Key` and `If-Match`/`expected_revision`.
- Writes require `Idempotency-Key`; concurrent updates are protected by `If-Match` or `expected_revision`.
- Telemetry delivery classification: `accepted`, `duplicate`, `retryable`, and `rejected` fold the per-event ACK ledger inside the requested time window; `gaps` counts persisted gap events. `queued` is a snapshot of the **server-side** delivery backlog. The fixture aggregates synchronously and cannot observe a Host queue, so it always reports `queued: 0` — a fixture-only value that must never be read as "real production backlog is zero". The production service owns the real snapshot.

## Tests

`pnpm exec vitest run apps/team-skill-service/tests` covers account and project authorization, Skill organization and project authorization, request validation, project memory, telemetry, and the governance lifecycle over real HTTP. These tests prove fixture behavior only.
## Cloud workspace fixture

- The fixture also serves the deterministic cloud workspace surface used by the plugin, Host, and admin closed loop: agent types, published project-bound agent profiles, workspace lifecycle (`provisioning` -> `starting` -> `ready`, plus stop/retry/archive/delete), remote directory and file reads, previews (`text`, `markdown`, `json`, `image`, `static_html` with a server-declared CSP and sandbox, and `diff`), changes against a baseline revision, runs with immutable configuration snapshots, replayable SSE at `/v1/events/stream` (unknown watermarks answer `resync_required`), and unified audit rows carrying the literal `actor_name` field.
- Every cloud workspace response carries `x-fixture-only: true`. Lifecycle transitions advance when a read observes them, retention pruning and event replay are fixture scenarios (`x-fixture-scenario: workspace-prune-events`), and audit rows live only in memory. No real container, runtime, Git provider, agent execution, or durable audit exists behind these routes.
- Agent configuration governance: `/v1/me/agent-profiles` returns enriched published versions per project (description, agent-type name/key/readiness/capabilities, ordered Skill bindings with server-resolved names and readiness, knowledge-base set, a single memory library or `null`, execution policy with `write_mode`, generic `type_extension_config`, readiness verdict with reason, default mark, creator and timestamps); `/v1/admin/agent-types` plus `/v1/admin/agent-types/{id}/schema` serve per-type extension schemas (Claude Code, Hermes, and a retired `legacy_shell` type), `/v1/admin/asset-candidates` serves authorization and readiness metadata, and the profile lifecycle covers create, draft save (`If-Match`), new version (`If-Match` required), clone (new opaque id, no bindings, no published state), publish (blocks unavailable agent types, missing required extension fields, missing assets, unauthorized assets, and not-ready credential references), archive, bind (rejects unknown or cross-organization projects and assets the project is not authorized for, keeps one default per project across profiles), and unbind — each emitting an `agent_profile` stream event and an audit row with the literal `actor_name`. Write bodies must be JSON objects (`400 INVALID_RESPONSE` otherwise), binding flags are never defaulted, and a run's write mode may tighten but never widen the profile's declared `write_mode` (`422 AGENT_TYPE_UNAVAILABLE` also guards unavailable agent types for workspace and run creation).
- The fixture serves the `/v1` surface directly. A consumer configures `apiBaseUrl` as the service endpoint: a trailing `/v1` and a trailing slash are both optional because the Host normalizes to exactly one `/v1`, so `http://127.0.0.1:<port>` and `http://127.0.0.1:<port>/v1` reach every REST route and the SSE stream alike.
